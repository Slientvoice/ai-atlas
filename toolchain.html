这次盘点，看三处变化

01 · 硬件决定可选路径

ROCm 补齐 AMD 计算栈；TensorRT-LLM 已采用 PyTorch 原生架构。先查硬件与模型支持，再谈性能。

02 · 训练与推理接成循环

TRL、verl 将生成采样接入后训练。推理引擎也参与训练，权重同步和后端兼容成为配方的一部分。

03 · Agent 按层组装与验收

MCP / A2A 负责连接，SDK 负责执行；还要用任务评测检查结果，并用轨迹定位失败。

从任务入场：本地运行、微调、Agent 应用
  • 先在本机运行：核对模型与权重格式 → llama.cpp / Ollama → 检查内存、上下文和执行位置。
  • 做一个微调实验：LlamaFactory / PEFT 或 TRL → 记录配置与产物 → 固定评测集验证；资源不够时再设计分布式训练。
  • 交付 Agent 应用：选择编排层与执行 SDK → 接模型、数据和工具 → 接入观测 → 用自己的任务集验收，必要时参考公开基准。

ST.00地基与内核4 条目

从 GPU、内存与互联出发，选择能在目标硬件上运行的编译器、算子库和通信栈。对应蓝图 PLANE 0。

CUDA

GPU 平台

NVIDIA GPU 的并行计算平台：编译工具链、运行时、数学库与分析工具共同把模型计算落到设备上。

使用边界：CUDA 是一套软硬件生态。驱动、Toolkit、GPU 架构与框架构建版本需要匹配；更换加速器时，先核对支持矩阵。

原理在蓝图：0 · 为什么是 GPU · 0 · 屋顶线模型

官方来源：CUDA 官方文档 ↗

AMD ROCm

GPU 平台

AMD 的 GPU 计算软件栈，包含 HIP 编程接口、编译器、数学库与 RCCL 通信库，连接 PyTorch 等框架。

本次补入：官方已有 vLLM、SGLang 等推理部署入口。选型要同时核对 GPU 型号、操作系统与框架版本，不能仅凭“支持 AMD”判断可运行。

原理在蓝图：0 · 为什么是 GPU · 0 · 屋顶线模型

官方来源：ROCm 与兼容性入口 ↗

Triton

内核语言 / 编译器

用接近 Python 的语言编写 GPU 内核，控制数据块、访存和计算，适合定制矩阵运算、融合算子与注意力内核。

使用边界：仍需理解并行与内存布局，并针对目标设备测量。这一项目与 NVIDIA 的 Triton Inference Server 是不同工具。

原理在蓝图：0 · 为什么是 GPU · Ⅱ · 注意力

官方来源：Triton 文档 ↗

NCCL

GPU 通信库

为 NVIDIA GPU 提供 AllReduce、AllGather、ReduceScatter 等集合通信，以及点对点通信；根据互联拓扑组织传输。

使用边界：它承担“交换张量”，训练框架负责如何切模型与调度。多机效果还取决于网络、拓扑和进程配置；AMD 栈对应查看 RCCL。

原理在蓝图：0 · 互联与集群

官方来源：NCCL 概览 ↗

ST.01训练车间5 条目

从前向、反向与优化器到分布式训练、微调和强化学习。对应蓝图 Ⅰ 训练管线。

PyTorch / FSDP2

训练框架

PyTorch 提供张量、自动微分与模型模块；其分布式能力支撑单机实验到多机训练。

当前重点：FSDP2 用 fully_shard 与 DTensor 按参数分片，减少每个设备保存的模型状态。代价是额外通信，分片与检查点策略需一起设计。

原理在蓝图：Ⅰ · 预训练循环 · Ⅱ · Block 总装

官方来源：PyTorch FSDP2 ↗

Megatron / DeepSpeed

分布式训练

Megatron Core 是可组合的训练组件库，Megatron-LM 提供参考训练实现；DeepSpeed 则提供 ZeRO 等内存与训练优化。

如何区分：Megatron 的张量、流水线、专家等并行与 DeepSpeed 的状态分片解决不同问题，可按框架集成情况选择。两者无需固定捆绑；FSDP2 也是分片训练路径。

原理在蓝图：0 · 互联与集群 · Ⅰ · 预训练循环

官方来源：Megatron-LM / Core ↗DeepSpeed ZeRO ↗

TRL

后训练库

围绕 Transformers 组织 SFT、DPO、GRPO 等训练器，并集成 PEFT、DeepSpeed 与 vLLM，便于从一个后训练实验开始。

当前重点：官方文档已将蒸馏和异步训练纳入版图；部分训练器仍在 Experimental 区。实现前核对所装版本，文档 main 分支与稳定包可能不同。

原理在蓝图：Ⅰ · 监督微调 SFT · Ⅰ · 可验证奖励

官方来源：TRL 训练器与实验功能 ↗

verl

分布式后训练

基于 HybridFlow 的强化学习训练框架，协调策略更新、奖励计算与 rollout（生成采样），可组合 FSDP、Megatron、vLLM、SGLang 等后端。

当前重点：同步与异步 rollout、训练到推理端的权重同步成为关键工程环节。算法、奖励函数、后端版本与资源配置共同决定效果。

原理在蓝图：Ⅰ · 可验证奖励与推理训练

官方来源：verl 文档 ↗

LlamaFactory / PEFT

微调入口 / 适配库

LlamaFactory 提供 CLI 与 Web UI，将模型、数据模板和 SFT、偏好训练等配方接起来；PEFT 提供 LoRA 等参数高效适配方法。

使用边界：图形界面减少配置负担，仍需检查数据质量、聊天模板、显存与模型支持。适配器依赖基座版本，训练和分发还要遵循对应模型许可。

原理在蓝图：Ⅰ · 监督微调 SFT

官方来源：LlamaFactory ↗PEFT ↗

ST.02权重集散地4 条目

这一站区分托管平台、模型实现与文件格式。下载到权重后，还要找到匹配的运行环境。对应蓝图 Ⅱ 模型本体。

Hugging Face Hub

模型 / 数据托管

以版本化仓库分发模型、数据集与应用，模型卡记录用途、评测和许可；下载权重与调用 Inference Providers 是不同的使用路径。

当前重点：Hub 使用 Xet 做文件分块与去重；新加入的 Buckets 面向可变、非版本化的存储。可下载不等于可任意商用，应核对发布者与模型卡。

原理在蓝图：Ⅱ · 模型本体 · 延伸：🧬 谱系 · 权重许可与获取方式

官方来源：Hub 官方文档 ↗

Transformers

模型定义与加载

提供模型架构、分词与预处理、权重加载、生成和训练接口，连接文本、图像、音频、视频等模型与上下游框架。

使用边界：统一接口以已支持的架构为前提。新模型可能需要特定版本或自定义代码；成功加载也不代表高并发服务已经配置完成。

原理在蓝图：Ⅱ · Block 总装

官方来源：Transformers 文档 ↗

safetensors / GGUF

权重文件格式

safetensors 以张量数据格式避免 pickle 的反序列化执行风险，并支持高效加载；GGUF 在 llama.cpp 生态中承载模型张量与元数据，常见于量化分发。

使用边界：文件格式不保证模型质量、许可或仓库代码可信。量化类型、模型架构与运行器必须匹配，GGUF 也不等于所有模型的通用运行包。

原理在蓝图：Ⅲ · 量化

官方来源：safetensors ↗llama.cpp / GGUF ↗

ModelScope 魔搭

模型社区 / SDK

提供模型发布、下载与 SDK，包含 pipeline 推理、训练和评估接口，是获取模型与配套实现的一条路径。

使用边界：按官方发布账号、仓库版本与模型卡核对内容。它有自己的社区与工具，不能概括为 Hugging Face 的镜像；同名模型也要核对文件和版本。

原理在蓝图：Ⅱ · 模型本体 · 延伸：🧬 模型门派谱系

官方来源：ModelScope 官方仓库 ↗

ST.03推理机房5 条目

把权重变成可调用的服务；同时衡量首 token 延迟、生成速度、并发、显存和成本。对应蓝图 Ⅲ 推理与服务。

维护状态：Hugging Face TGI 已进入维护模式，官方建议新部署评估 vLLM、SGLang 或本地推理引擎；现有部署是否迁移仍应核对功能与运维成本。TGI 官方说明 ↗

vLLM

推理 / 服务引擎

以 PagedAttention、连续批处理等机制管理推理资源，提供模型服务接口；现有能力涵盖前缀缓存、结构化输出、量化与多种并行策略。

当前重点：预填充与解码分离、推测解码、工具与推理输出解析都进入服务层。不同硬件、模型和后端的功能支持并不一致，选型以实际负载压测。

原理在蓝图：Ⅲ · KV 缓存 · Ⅲ · Prefill / Decode

官方来源：vLLM 官方仓库 ↗

SGLang

推理 / 服务框架

面向语言与多模态模型的服务框架，RadixAttention 与前缀缓存复用请求中的公共内容，支持从单设备到分布式部署。

使用边界：官方列出多类加速器与强化学习集成。前缀复用可能有利于多轮或 Agent 负载，但缓存命中率、调度和模型会改变收益；不能直接断言比 vLLM 快。

原理在蓝图：Ⅲ · KV 缓存 · Ⅳ · 上下文拼装 · Ⅲ · 采样

官方来源：SGLang 文档 ↗

TensorRT-LLM

NVIDIA 推理栈

NVIDIA 面向自家 GPU 的推理库，当前采用 PyTorch 原生架构，并提供高层 Python LLM API，覆盖多 GPU、多节点与量化等能力。

更新认知：“换模型都要先编译 TensorRT engine”已无法描述当前架构。能否使用某种精度或优化，仍取决于模型、GPU 与功能支持矩阵。

原理在蓝图：Ⅲ · 量化 · 0 · 为什么是 GPU

官方来源：TensorRT-LLM 架构概览 ↗

llama.cpp

跨硬件推理

C/C++ 模型推理实现，支持 CPU、Metal、CUDA、HIP、Vulkan 等后端，以及量化、CPU/GPU 混合执行和服务接口。

当前重点：覆盖语言与受支持的视觉语言模型，也能部署到服务器。可运行的模型、上下文长度和并发，仍受内存、量化与后端能力约束。

原理在蓝图：Ⅲ · 量化

官方来源：llama.cpp 与后端列表 ↗

Ollama

模型运行与服务入口

通过应用、CLI 和 API 管理模型与对话，既能在本机运行下载的模型，也可调用 Ollama 的云端模型。

关键区别：带 :cloud 等云路由的模型由远端执行。需要本地处理时，应选择本地模型并核对云功能和外接工具的设置；“在电脑里打开”不能证明推理发生在本机。

原理在蓝图：Ⅲ · 量化 · 延伸：🧬 谱系 · 权重许可与获取方式

官方来源：Ollama 本地 / 云端路径 ↗

ST.04组装车间6 条目

把模型、检索、工具、状态和执行环境连接成应用。框架、协议、SDK 与托管平台各有职责。对应蓝图 Ⅳ 系统组装。

LangChain / LangGraph

Agent 编排

LangChain 提供模型与工具集成及高层 Agent 接口；LangGraph 提供更底层的有状态图执行、持久化和人工介入能力。

当前关系：LangChain 的 Agent 构建在 LangGraph 之上；Deep Agents 再提供文件系统、上下文管理等配套能力。按需要控制的层级选用，持久化与恢复需要正确配置。

原理在蓝图：Ⅳ · 多智能体编排 · Ⅳ · 工具与 Agent

官方来源：LangChain 与分层关系 ↗LangGraph ↗

MCP / A2A

连接与协作协议

MCP 规范应用如何接入外部工具、资源和提示；A2A 让独立 Agent 发现彼此、委派任务与交换结果。两者解决不同层次的互操作。

使用边界：协议并不提供完整 Agent 运行时，也不会自动决定授权和信任。OpenAI Assistants API 的官方迁移方向是 Responses API，MCP 是其中可用的工具连接方式。

原理在蓝图：Ⅳ · 工具协议（含报文显微镜实验室）

官方来源：MCP ↗A2A 与 MCP ↗Assistants 迁移说明 ↗

OpenAI Agents SDK / Claude Agent SDK

Agent 执行 SDK

OpenAI Agents SDK 在应用中运行 Agent 循环，组织工具、交接和追踪；Claude Agent SDK 将 Claude Code 的工具、循环与上下文管理提供为 Python / TypeScript 库。

本次补入：SDK 适合将执行逻辑接入自己的产品。部署、状态与权限仍需配置；各厂商的托管 Agent 服务是另一种运行方式，不能与 SDK 混为一项。

原理在蓝图：Ⅳ · 多智能体编排 · Ⅳ · 工具与 Agent

官方来源：OpenAI Agents SDK ↗Claude Agent SDK ↗

LlamaIndex

数据与 Agent 框架

组织数据接入、解析、索引、检索与问答，也提供事件驱动的 Workflows 和 Agent，把 RAG 管线作为工具接入更长的任务。

使用边界：文档解析、检索质量与引用正确性要分别评估。开源框架与 LlamaCloud 等托管服务有不同的部署和数据处理路径。

原理在蓝图：Ⅳ · RAG

官方来源：LlamaIndex 框架文档 ↗

Dify

可视化应用平台

以可视化工作流连接模型、知识库、工具与 Agent，可选择自托管或云服务，并提供应用发布与观测入口。

使用边界：上线仍需要配置凭据、数据接入与运行环境。仓库采用附加条件的 Apache 2.0 许可，包含多租户服务及前端标识限制，部署前应阅读许可原文。

原理在蓝图：Ⅳ · 工具与 Agent

官方来源：Dify 官方仓库 ↗Dify 许可 ↗

Langfuse / LangSmith

观测与应用评估

收集模型、检索和工具调用轨迹，将延迟、成本、反馈与评估数据连接起来。Langfuse 支持 OpenTelemetry；LangSmith 支持多种框架与部署方式。

使用边界：能看到什么取决于埋点、采样和保留配置。有轨迹便于定位故障，但重跑仍受模型随机性和外部工具状态影响。

原理在蓝图：Ⅳ · 多智能体编排（编排剧场实验室的「日志」就是它的雏形）

官方来源：Langfuse ↗LangSmith Observability ↗

ST.QC质检站4 条目

分别检查模型答题、任务完成、用户偏好与运行表现。它们互相补充，分数不能直接互换。对应蓝图 Ⅰ 评估·红队·发布。

lm-evaluation-harness / OpenCompass

自动评测框架

前者提供可复用的语言模型任务与评估后端；后者组织模型、数据集、提示模板和评测流程，也支持主观评价与代码任务。

如何读结果：同时记录模型与数据版本、提示模板、few-shot 设置、推理预算和评分方法。框架能统一流程，不能消除数据污染或评判模型的偏差。

原理在蓝图：Ⅰ · 评估·红队·发布

官方来源：lm-evaluation-harness ↗OpenCompass ↗

SWE-bench / Terminal-Bench

Agent 任务评测

SWE-bench 以真实仓库问题检验代码修复；Terminal-Bench 在可执行环境中考察终端任务，报告完成率，并展示成本等指标。

本次补入：任务成绩属于“模型 + Agent 实现 + 工具环境”的组合。比较时固定数据子集、环境、预算与重试次数；不同版本的榜单不可直接拼成模型排名。

原理在蓝图：Ⅰ · 评估·红队·发布

官方来源：SWE-bench ↗Terminal-Bench ↗

Weights & Biases

实验与模型管理

W&B Models 记录实验配置与指标，管理数据、模型版本和产物关系，并支持超参数搜索与协作。

如何使用：把训练曲线、评测结果与对应检查点绑定，才能追溯哪组设置有效。指标采集、告警与上传范围需要配置，监控记录不等于质量通过。

原理在蓝图：Ⅰ · 预训练循环

官方来源：W&B Models ↗

Arena（LMArena）

人类偏好评测

通过匿名成对比较收集用户偏好；文本偏好榜使用 Bradley–Terry 模型聚合投票，并提供风格控制等方法。

如何读结果：偏好得分反映特定用户与问题分布，不等于事实正确率或任务完成率。选型时结合样本量、不确定性及自己的任务集，避免把盲测称为“无法刷榜”。

原理在蓝图：Ⅰ · 评估·红队·发布

官方来源：Arena 方法说明 ↗

ST.DEV你手边的工具2 条目

贯穿所有工位的开发工作台：记录改动、协作审查，让 Agent 的产出成为可检查的工程结果。

Git / GitHub

版本管理与协作

Git 在本地记录提交与分支；GitHub 提供远程仓库、Pull Request 等协作入口。代码、配置与评测方案可以在同一套版本记录中关联。

使用边界：提交历史帮助追溯和回退，但不自动证明作者身份或内容正确。大权重、数据与运行产物应结合合适的存储方案管理。

工程实践：本站建设台账 · 站点仓库

官方来源：Git 与 GitHub 的区别 ↗

Claude Code / Codex / Cursor / Copilot
